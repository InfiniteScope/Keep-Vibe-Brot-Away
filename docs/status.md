## 已知限制

### 1. 测试结果没有权威语义

事件协议能保存测试命令，但没有标准退出码或 `passed/failed` 字段。当前 WorkUnit 中的测试状态为 `Unknown`，因此不能声称“测试已通过”或据此形成可靠的测试失败风险。

下一步应先扩展事件协议和各适配器的能力声明，再让聚合器消费结果；不能从命令文本猜测成功。

### 2. 高风险主动展开当前不可达

队列只会为置信度至少 0.85 的 P0 或 P1 洞察主动展开，但生产分析器目前只生成 Info 或 P2。现状是“策略已接好，风险来源未接好”，不是完整的主动风险提醒。

### 3. Git 快照不是回合差异

当前只在回合结束读取相对 `HEAD` 的工作区：

- 无回合开始基线。
- 本轮已提交的修改可能不可见。
- 共享工作区变化无法归因给单个 Agent。

要获得精确归因，需要保存回合开始状态，并处理提交、重写历史和多 Agent 并发。

### 4. 适配器证据质量不一致

- Claude Code Node 与 Rust 样例都使用异步钩子，工具事件与边界的到达顺序不具备强保证，也都未接 `PostToolUseFailure`。Rust 样例只订阅 `PostToolUse` 与 `Stop`。
- Claude JSONL watcher 没有回合边界，只走旧门控。
- Codex 只有回合完成通知，没有逐工具和测试结果。
- Trae 的工具响应字段不等同稳定的进程退出状态。
- 双路同报按内容指纹判重时，可能保留重复事件，也可能在证据粒度不同时丢掉更精确的一条。

### 5. 端点发现仍有平台缺口

`KVBA_DATA_DIR` 只影响适配器，不影响主程序。macOS 适配器默认使用 `~/.local/share/dev.kvba.app`，而 Tauri 主程序通常使用系统应用数据目录，两端可能找不到同一份 `endpoint.json`。

在修复前，macOS 需要先确认主程序实际目录，再为 Agent 进程设置指向该目录的 `KVBA_DATA_DIR`。这项流程尚未做实机闭环验证。

### 6. 事件日志只有条数上限

`events.log` 只保留最近 200 条，但没有总字节上限。200 条长事件仍可能让单个日志文件异常偏大。

### 7. LLM 端到端验证不属于 CI

CI 覆盖契约解析、SSE 处理和相关单元测试，但不会使用真实提供商密钥。设置面板“出稿来源”出现 LLM 计数，才是当前实例实际完成过模型出稿的证据。

### 8. 目标架构尚未完成

RFC-0003 中的 ProjectModel、UserModel、SQLite 投影库、多投递端和 20 个真实任务回放仍未落地。当前 `facts.json` 记忆层与旧门控属于兼容实现，不应被描述为最终认知模型。

### 9. 新洞察尚未接入动作闭环

“不满意 → 生成下一轮优化提示词”只对旧链路的 `review` 卡片生效。新的 Insight 主投影当前使用 `tips` 卡片类型，因此用户反馈不会触发优化提示词。

## 下一步建议

按依赖顺序推进：

1. 为事件协议增加可选的执行结果和适配器能力声明，先打通一条真实测试失败链路。
2. 让风险等级来自可验证证据，再开放 P0 或 P1 主动展开。
3. 引入回合开始基线，明确提交内变更和共享工作区的归因规则。
4. 修复跨平台端点发现，让主程序与适配器共享同一目录解析逻辑。
5. 为 `events.log` 增加字节预算和截断策略。
6. 用至少 20 个真实任务回放评估洞察价值，再推进 ProjectModel/UserModel 和 SQLite。

方向与验收指标见 [RFC-0003](rfcs/RFC-0003-workunit-cognition-ledger.md)。开放工作应以 GitHub Issue 为准，本页只维护会影响使用和架构判断的限制。
