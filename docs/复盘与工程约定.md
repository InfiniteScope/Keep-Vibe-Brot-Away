## 一、最贵的一个错：把单位错误当成根因交付

**现象**：用户报告「托盘图标在，桌面圆点不在」。

**我的结论（错的）**：`settings.json` 里遗留的 `dockX=2358` 超出了屏幕宽度，圆点画在屏外，所以看不见。我还为此写了钳制逻辑、加了 6 个单测，并把这段因果讲给了用户。

**它是怎么被推翻的**：提交前我复核了一遍数字，发现 `dockX=2251 + 72 ≤ 屏宽` 看起来又不越界了——同一套代码给出两个矛盾的结论，说明**前提有问题**。于是我改用 DPI-aware 的 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 重测：

```
WinForms  AllScreens  → 1707 × 1067     ← DPI 虚拟化后的「逻辑」值
GetSystemMetrics(0,1) → 2560 × 1600     ← 真实物理像素,DPI 150%
Tauri 落盘的坐标      → 物理像素
```

我拿 DPI 虚拟化的 1707 去比物理的 2358。**2358 + 72 = 2430 ≤ 2560，圆点从来没出过界**，钳制代码在用户机器上是空转。

**规矩**：

1. 跨层比较数字之前，先确认每一层的单位与坐标系。Windows 上任何几何结论必须来自 **DPI-aware** 测量；`System.Windows.Forms.Screen` 在未被标记为 per-monitor aware 的宿主里返回的是虚拟化的逻辑值。
2. 一个假设如果被它**解释不了的现象**（比如 2251）反驳了，那要先解决矛盾，而不是先收尾。
3. 结论必须带前后证据。没有实测支撑的因果链，写进文档时要标成「猜测」，不能写成「根因」。
4. 允许自己推翻自己，但必须显式写明「已否证」。在调试记录里保留被否证的假设和否证它的证据，这比只留下成功路径有价值。

顺带一条诚实记录：**「圆点看不见」这个现象我最终没找到代码级原因**（最可能是当时处于面板展开态——`show_panel_mode` 会 `dot.hide()`——或那个实例已退化，重启即恢复）。它没有闭环，我不给它编一个原因。

## 二、第二贵的错：三轮「重启就好」，而适配器从来没装过

用户连续三次报告「还是无法触发」。我三轮都在改**代码**：统一指纹口径、拆出 `InsertOutcome` 三结局、给 facts 加 in-flight 去重、把预算重复计费修掉……每一处改动本身都对，**但没有一处是当时的阻塞点**。

真正的阻塞点是一条 `Test-Path` 就能查出来的事实：

| 取证 | 实测 |
|---|---|
| `events.log` 内最大 ts | 25 小时前 —— **零事件流入** |
| `.trae/hooks.json`、`~/.trae-cn/hooks.json` | **两个都不存在** |
| `projects/` | 两个目录，分别是 `C:\Users\...\KVBA` 与 `c:/Users/.../KVBA` |
| `projects/*/` | 都**只有 events.log，没有 facts.json** |
| `budget.json` vs `stats.json` | LLM 用 21 次，今日发卡 1 张 |
| 端口 50479 | 无监听、无进程 |

完整因果链（每一环独立致命）：

```
hooks.json 从未创建 → Trae 零上报 → 25h 无事件
  → kick_facts 只在事件流入时调用 → facts.json 永远不存在
  → 主题恒为 framework-unknown → 知识分支每次让 LLM 写同一句话
  → 正文指纹 == 20min 内那张 → Duplicate
  → 用户点「来一道」只看到「刚递过同款内容」,队列永远 0/3
```

**规矩**：

1. **先证明输入到达，再调试流水线。** 任何「没反应」类问题，第一动作是查数据面证据（日志文件、落盘时间戳、对端文件是否存在），不是读代码。我这三轮的耗时几乎全部花在一条 `Test-Path` 就能省掉的路上。
2. **区分「代码缺陷」与「现场缺配置」。** 用户机器上少一个文件，比任何逻辑 bug 都更常见、也更难靠读代码发现。安装类步骤要有**可自证的判据**（见第三节）。
3. 让用户执行「重启一下」这类动作前，必须先说清**为什么重启会有效**、以及**如果无效下一步查什么**。说了三次「重启就好」而没给出判据，等于把排查成本转嫁给用户。
4. **Trae hook 生效有两个不可跳过的条件**：设置 → Hooks 里必须处于**启用**态；配置只在 **Session 创建时**读取，改完必须新开会话。当前会话内无论怎么改文件都不生效。

### 二·补：第三轮——hook「已启用」但一次都没执行（实测确认）

第二轮的结论是「`.trae/hooks.json` 从未创建」。第三轮它**已创建、已在 UI 里启用**，事件仍然为零。这次的真凶不是缺文件，是**路径里的一个空格**。

**现象**：Trae「输出 → Agent Hooks」面板里，每次工具调用都刷同一坨：

```
error: unexpected argument 'more\KVBA\adapters\trae-hook\kvba-trae-hook.mjs' found
Usage: trae-sandbox.exe exec [OPTIONS] ... --command-line <COMMAND_LINE>
```

**逐层排除**（每一层都单独看起来"正常"，这是它难查的原因）：脚本手动管道喂 payload → `[kvba-hook] Stop → ok`；KVBA 进程在跑；`endpoint.json` 端口/token 有效；`hooks.json` JSON 合法、`matcher:"*"`、UI 显示已启用。**唯一断点是命令拼接。**

**根因**：Trae 把 hook 命令交给 `trae-sandbox.exe exec --command-line <...>`，命令串里的**内层引号会提前闭合外层引号**，于是路径在空格处被劈成两半——`node "C:\...\GH` 进了 `--command-line`，`more\KVBA\...\kvba-trae-hook.mjs"` 变成多余位置参数。

**所以「给路径加引号」这个直觉解法是无效的，加了照样断。** 唯一稳的写法是**路径无空格 + 完全不加引号**，仓库本身带空格时用 8.3 短路径：

```powershell
# cmd /c dir /X 在沙箱里被禁,用 COM 取短名
(New-Object -ComObject Scripting.FileSystemObject).GetFolder("C:\...\GH more").ShortPath
# → C:\...\GHMORE~1     命令写成: node C:\...\GHMORE~1\KVBA\adapters\trae-hook\kvba-trae-hook.mjs
```

**最难看的一条**：这个坑是**我自己写进模板的**——`adapters/trae-hook/hooks.sample.json` 原文就是 `node \"<绝对路径>\\...\"`，带内层引号。任何仓库目录含空格（或中文）的用户照抄即中招。已改。

**新增规矩**：

5. **「已启用」不等于「能执行」。** 安装类配置要有**一条不经过宿主包装层的自证路径**：直接管道喂 payload 给脚本。本轮若第一步就做这个，会立刻看到「脚本自己没问题」，从而把范围从整条链路收窄到宿主拼接层。
6. **示例配置里不要给路径加引号**——它只在路径含空格时才是必需的，而那时它恰恰是致害的那一层。正确做法是要求路径无空格，并把短路径方案写进文档。
7. **模板即产品**。`hooks.sample.json` 里的一处错误写法，等于给每个照抄的用户预装一个故障。

## 三、静默吞错与「二值假诊断」

`let _ = std::fs::write(...)`、`unwrap_or_default()`、`match ... { _ => {} }` 在这里不是风格问题，它们每一个都对应一次「用户看不出为什么坏了」。

真实后果 A：端点发现文件 `endpoint.json` 写入失败被完全吞掉，而读取端会**回退去读上一次进程留下的陈旧文件**——端口是上一个实例的，早就没人监听了。于是应用「运行正常」，适配器永远 401，而且现场看起来一切正常。

真实后果 B（本轮新增）：设置面板「最近事件」一栏的判据是 `lastEventIn != null → 链路正常`。而 `lastEventIn` 只要**落过一条**事件就永远非空——于是它连续 25 小时显示「链路正常」，把断流完全掩盖。**一个只会变绿的二值指示器，比没有指示器更有害。** 现已改为「本次进程摄入 N 条 · 最近 X 分钟前」，并显式区分三态：0 条＝适配器未接入 / 有历史但 >10min 静默＝链路曾通后断 / 正常。

### 三·补：第三轮——日志「有」，但它在结构上无法回答那个问题

上一轮的交接里我写过一句**现在必须作废**的话：

> ~~若仍失败，先看控制台那行 `facts 首版返回不可解析的 JSON(前 240 字)` —— 失败原因已经会打出来，不要靠猜。~~

**它做不到它承诺的事。** 那行日志把两种**修法完全相反**的故障压成了同一个 `None`：

| 真实故障 | 该做的动作 | 日志给的线索 |
|---|---|---|
| 输出被 `max_output_tokens` 截断（`extract_json` 扫不到闭合 `}`） | 提高 token 上限 | 「不可解析」 |
| JSON 完整但字段类型与契约不符 | 改契约或放宽结构体 | 「不可解析」 |

而且**只留头部 240 字**——可截断的判据恰恰只在**尾部**（停在数组/字符串中间）。47 次失败、47 行日志，没有一行能回答「该提 token 还是该改契约」。

**实测确认的根因**：`kick_facts_if_needed` 用 `max_output_tokens = 400`，卡片路径 `analyze_pass` 用 800。同一份契约、同一个解析器、两条路径两个上限；400 装不下 `dirSummary`（契约允许 ≤80 字中文）加两个数组，模型每次在闭合 `}` 之前被掐断 → `extract_json` 返回 `None` → 只 `log::warn!`、不重试、不落盘 → `facts_inflight` 释放 → **下一条事件再烧一格**。单日 `budget.used=52` 里 **47 格**烧在这条循环上，日志里 47 行失败与它精确对上。

> ## ⚠️ 上面这条「实测确认的根因」是错的，本条作废（第四轮，就地更正）
>
> **错在哪**：`max_output_tokens` 提到 800 之后，故障**一模一样地复现**。新加的诊断立刻给出了铁证——响应**全文只有 65 / 82 / 87 / 100 / 104 字**，离 800 的上限差着一个数量级。截断与 token 上限无关。
>
> **真根因（这次有可执行的证明）**：`llm/providers.rs::sse_lines` 的 `unfold` 状态机**每个网络块只吐出一行 `data:`**，其余全压在缓冲区等下一个块；流一结束，残留的多行被 `trim()` 成**一坨**交给 `serde_json` → 解析失败 → `Err(_) => String::new()` → **静默丢弃**。服务器把最后几个 delta 攒进同一个 TCP 写里发出是 SSE 常态，于是每次都在 JSON 中间断掉。
>
> 我用泛型化 `sse_lines` 让它可测，写了三条测试。在**旧实现**上：
>
> ```
> multi_line_chunk_must_emit_every_data_line ... FAILED   left: 2, right: 3
> multibyte_char_split_across_chunks_must_survive ... FAILED  "框架" → "架"
> final_chunk_without_trailing_newline_must_not_lose_lines ... ok  ← 我这条猜错了
> ```
>
> 修完（字节缓冲 + 每块排空所有整行 + 尾块按行冲刷）三条全绿。附带修掉 `from_utf8_lossy` 先解码再找换行导致的跨块多字节字符变 U+FFFD——**UTF-8 的 0x0A 只可能是行终止符**，按字节切行天然不会劈开汉字。
>
> **我是怎么被骗的（这条最值钱）**：我拿「卡片路径用 800 且成功」当作排除传输问题的证据。但卡片在契约解析失败时会 `normalize_out(AnalysisOut::default())` → **把空正文回填成模板文案 → 照样入队 → 决策日志照样记 `G7 pass=true 卡片生成并入队`**。查 `history.json` 实得：5 张卡里 **4 张正文逐字命中模板原文**，`optimizedPrompt` 非空 **0 次**——「不满意→优化提示词」这个杀手闭环**从未真正产出过**。
>
> 也就是说：**我用来做排除证据的那个指标，本身是不可证伪的假绿灯。** LLM 契约路径从头到尾 100% 失败，卡片靠静默兜底伪装成健康，facts 没有兜底才露了馅。
>
> **新增规矩**：
>
> 1. **不要用「另一条路径看起来正常」作为排除证据，除非那条路径的成功判据本身可证伪。** 判据：这个"成功"有没有可能由兜底逻辑产生？答不出来就不能拿它当证据。
> 2. **改因和加诊断不要混在一次改动里。** 我同一次既提 token 又加诊断——诊断是对的、救了后面所有轮次；token 那次是纯猜。**先只加诊断，跑一轮，让证据选假设，再动手。** 这次侥幸两件事一起做，才没多耗一轮。
> 3. **静默兜底必须自带可观测性。** 已修：`AnalysisOut.from_llm`（`#[serde(skip)]`）+ 决策日志区分「LLM 出稿 / 模板兜底」+ `Stats.cards_llm / cards_template` 分账 + 设置面板新增「出稿来源」行。正文被模板回填时来源**改判**为兜底——契约解析成功不等于这句话是 LLM 写的。

已修：`parse_contract_facts` 返回 `Result<Facts, FactsParseErr>`（`Unclosed` / `Shape` 两态）；新增 `text_probe` 带**长度 + 首尾**；仅「调用成功但解析失败」才走一次免预算严格重试；连败 3 次冷却 6 小时。~~上限对齐 800~~ —— 这个数本身在第五轮被消灭了，见下节。

**新增规矩**：

0. **诊断信息必须能证伪它自己的至少两个候选假设。** 做不到就不要在交接里声称「原因已经会打出来」——那句话把下一位排查者引向一次注定无果的读日志。判据：如果一条日志对所有已知故障形态都输出同一句话，它等于没有输出。
0b. **截断类故障的证据只能在尾部。** 打印任何「疑似不完整」的外部输入时，长度 + 头 + 尾三者缺一不可。
0c. **同一份契约的多条调用路径必须共用一个取稿函数。** facts 与卡片各写一遍 `chat_complete + parse`，就会各写一遍 token 上限和错误处理——这次的 400/800 差异没有任何设计意图，纯属漂移。

**还有一条本轮新踩的（PowerShell）**：`Select-String` 的 pattern 里含**反引号**会打断字符串解析，报「字符串缺少终止符」；`cmd /c dir /X` 在沙箱内被禁，取 8.3 短名要用 `Scripting.FileSystemObject.ShortPath`。

### 三·补2：第五轮——「够不够大」是伪问题，消灭它而不是回答它

第四轮我把 facts 的上限从 400 提到 800，并宣称「与卡片路径对齐」。用户回了一句：

> **「max_output_tokens 也不够大吧」**

**这句是对的，而且它指出的问题比它本身大得多：只要还存在一个手写的上限，「够不够大」就永远是个悬案。** 我上一轮花三小时误判根因，起因就是 `facts=400 / 卡片=800` 这两个各自为政的数字——它们既没设计意图，又随时在暗示"也许是小了"。

**照做（调大）反而有真实反作用**：`max_tokens` 超过 provider 自身硬上限会直接吃一个 `400`，故障从「静默截断」升级成「完全不通」。所以"更大"不是更安全，是换个死法。

**正确的动作是消灭这个问题**：不下发 `max_tokens`，让 provider 用自己的最大值。

```rust
pub const MAX_OUTPUT_TOKENS: Option<u32> = None;      // 全仓唯一取值点
pub struct ChatRequest { pub max_output_tokens: Option<u32>, … }
```

| Provider | `None` 时 |
|---|---|
| OpenAI 兼容（含 DeepSeek） | body 不带 `max_tokens` |
| Google Gemini | `generationConfig` 不带 `max_output_tokens` |
| Anthropic | **该 API 强制要求此字段**，不能省略 → 回退 `ANTHROPIC_REQUIRED_MAX = 8192` |

四处调用点（卡片首稿 / 卡片严格重试 / facts 首版与增量合并 / 优化提示词）全部收敛到这一个常量，并加回归锁：

```rust
fn output_cap_is_left_to_the_provider_not_a_local_number() {
    assert!(MAX_OUTPUT_TOKENS.is_none(), "…不要回到各调用点各写一个数");
}
```

**「删掉一个数」比「改大一个数」多花的成本**：三家 API 对这个字段的可选性不一样，所以它不是一行改动，而是要按 provider 分叉。**遇到这种情况值得多写那几行——把不可证伪的悬案从代码里物理移除，比留一个"看起来够大"的数字便宜得多。**

**顺带一条差点踩空的坑**：规格 §1.3/§6/§7.3 写着「单次分析强制 ≤5000 token」，我一度以为删上限就是违反硬约束。想清楚才确认——**那约束的是实际消耗，而实际消耗由输入侧决定**（`system` ≈0.6k + `user` 经 `fit_tokens` 裁到 ≤3.5k），这两处裁剪一行没动；输出侧另有解析后 `text > 120 字` 的硬截断兜底。已在 §7.3 就地补注口径。**读规格要读它约束的对象，不能只读数字。**

**新增规矩**：

4. **如果一个参数只是在制造「够不够大」这种无法回答的问题，就该删掉它，而不是调它。** 判据：给出任何值你都没法论证"这个值对"，那这个值本身就是错的抽象。
5. **代码改了，凡是陈述因果的文案都要回扫。** `FactsParseErr::Unclosed` 原文案是「输出被 `max_output_tokens` 截断」——上限一旦不再下发，这句话**立刻变成新的误导源**。注释、断言消息、日志文案、错误提示里的因果陈述，和被改的代码同属一次提交。
6. **规格里的数字要先问它约束的是什么。** 「≤5k token」看着像上限，实际约束的是消耗量；把它当上限去遵守，就会为了一个不存在的约束保留一个制造悬案的数字。

**规矩**：

1. 边界（文件系统、网络、注册表、IPC）失败**必须留痕**。落盘类操作走统一入口，失败时 `log::error!` 带上**绝对路径 + 影响面**，例如：
   `写入 ...endpoint.json 失败:拒绝访问 —— 适配器将无法发现本地端点(KVBA 本体仍可用)`
2. **真相源不要放在可能陈旧的旁路文件里**。本次进程的端点已经收进内存 `OnceLock`；读不到就显示「未启动」，绝不显示上一次的端口。
3. 不要用 `unwrap_or_default()` 兜底写出一个「结构正确但内容空/假」的文件。空文件比不写更难查。
4. **健康指示器必须带新鲜度与计数**，不能只有布尔。「曾经成功过一次」不是健康。
5. 给「不可能发生」的分支留 `debug_assert!` + 注释 + 确定性兜底；**不要**为了让某条测试通过而在实现里保留 `unreachable!()` 分支。测试不该固化「不会发生」的路径。

## 五、我写错的结论：否定性断言最便宜，也最危险

同一轮里我犯了两个方向相反、代价相同的错。

**错 A：把「我没搜到」写成「它不存在」。** 我在审计报告里断言「`p0ReplaceQueue` 是假开关——设置面板有，Rust `Settings` 无此字段，勾上完全无效」。实际 `Settings.p0_replace_queue`、`SettingsPatch`、`insert_card` 的替换分支和单测**全部存在**。错因：我拿前端的驼峰名 `p0Replace` 去 grep Rust 的蛇形字段 `p0_replace_queue`，零命中就下了结论。serde 的 `rename_all = "camelCase"` 正是为了让两侧名字不同而存在的。

**错 B：把「它存在」写成「它不存在」——通过委托放大。** 我用一个检索子代理逐条核实 18 项断言，它正确地揪出原报告里 4 条**根本不成立**的名字（`dedup_check`、`core.recently_asked`、`capsule:panel-head`、`blake16` 在源码里都不存在），这份产出质量很高，我据此重写了报告。但**同一份产出漏掉了 `p0_replace_queue`**，而我因为「它前面 17 条都对」就照单全收。

**错 C（第三轮）：把「我没查依赖的默认值」写成「它没有这个能力」。** 我断言「`tauri_plugin_log` 只设了 `level(Info)`、没有文件 target，所以独立运行的 exe 里连 warn 都看不到」，并据此提议**新增**一个 `LogDir` target。实际 `Builder::new()` → `Default::default()` 的默认 target 就是 `[Stdout, LogDir]`，`%LOCALAPPDATA%\dev.kvba.app\logs\KVBA.log` **一直在写**，那 47 次 facts 失败全在里面。

错因：我只读了本仓库那三行 `Builder` 调用，凭对 API 的印象下结论，**没打开依赖 crate 的 `Default` 实现**。差一点就交付一处完全无用的改动。这条尤其难看——它是下面规矩 1 的变种，而我上一轮刚把它写下来。

真正的病不是「没有日志」，是「**没人知道日志在哪**」。已改为在 README「数据目录」一节写明各平台路径，并显式提示日志不在 `%APPDATA%\dev.kvba.app\` 里。

**错 D（第五轮）：又一次「我的查询没命中」被写成「它不存在」。** git push 失败报 `Failed to connect to ... over proxy 127.0.0.1:33210`，我随即断言「**33210 现在没有监听者**」，并解释那 4 条 `Established` 是别的进程恰好用到了这个本地端口。

实际 `33210` **一直在监听**，属主是 `uniproxy`（pid 10892），系统代理也已启用指向它。错因：我用 `Get-NetTCPConnection -LocalPort 33210 -State Listen` 逐端口扫，没命中；换成 `Get-NetTCPConnection -State Listen | Where LocalAddress -in 127.0.0.1/0.0.0.1/::1` 就出来了。**同一个对象，两种写法，一个漏一个中。** 这是第五节规矩 1 的**第三次**犯规，而且这次我连"再换一种查法确认一下"都没做就下了结论。

顺带一条同源错误：用户贴的那份终端转储（881 行）末尾停在 `could not compile due to 12 previous errors`，我差点把它当成**当前**状态叙述。它是 18:11 的**历史快照**，不是实时状态——真正要问的是"现在有没有进程"，一条 `Get-Process` 就够。**日志文件默认是过去时。**

**规矩**：

1. **任何「不存在 / 未实现 / 没有调用点」的断言，必须给出你搜了什么、以及为什么这个搜索足以覆盖。** 跨语言契约尤其要**两侧各查自己的规范名**，不能拿一侧的序列化名字去猜另一侧。
2. 下否定性结论前，做一次**反向确认**：直接打开那个文件读那几行。成本 5 秒，比撤回一次结论便宜两个数量级。
3. **子代理的产出不是地面真相**，尤其是它的沉默。它可以作为线索来源，但写进文档的每条断言我要能自己复现。
4. 发现写错就在**原文里就地更正**，保留「本条作废 + 错因 + 教训」，不要静悄悄删掉。上一轮的误判我留了，这一轮的也留着。
5. **断言某个能力/字段/输出不存在之前，先查依赖 crate 的默认实现。** 只看自己这一侧的调用点远远不够——`Builder::new()` 的行为不由你写的那几行决定。
6. 提出「新增 X」之前，先证明「X 现在真的没有」。本轮只要先 `Get-ChildItem` 一次日志目录，就不会有那处多余改动。
7. **否定性结论必须换一种查法复验。** 同一份数据用两种独立方式查（按端口过滤 vs 全量枚举再筛），成本 5 秒。这是规矩 1 的执行细则——**"我再搜一次"要用不同的搜法，否则只是把同一个盲区再看一遍。**

## 六、铁律（优先于任何新特性）

1. **绝不阻塞 Agent**。适配器与 hook 失败一律重试后静默丢弃，并**以退出码 0 结束**。任何让 Agent 卡顿、报错、弹权限的东西一票否决。
2. **优雅降级**。LLM 不可用 → 只出模板卡；额度耗尽 → 攒批不硬打（恢复后**不追发**，这是设计而非缺陷）；端点不可用 → KVBA 本体照常用。
3. **失败要能看见**（第三节的规矩就是它的配套）。
4. **知情度卡必须最后生成**：它是唯一能让 Agent 反问「项目用什么框架」的卡型，先出就等于抢走真正该递的话。
5. 事件契约（`kvba.event.v1` + 门控流水线）与端点发现文件是**协议边界**。新增第 4 个 Coding Agent 不该改动核心，只该写一个能吐这个 schema 的上报脚本。
6. **门控的拒绝原因必须是可执行的**。写「队列已满或同指纹重复」这种二选一假提示，等同于把用户推进死路；三结局必须分别陈述，且陈述的是**真实发生的那一个**。

## 九、给协作者的话

- **先量，再动手。** 两轮里最贵的都不是代码，是我先给了一个错的根因、又连着三次让用户「重启一下」。带单位的观测值比合理的叙事可信；叙事再顺也不能替代一次 `Test-Path`。
- **先证明输入到达，再调试流水线。** 数据面的 5 分钟取证，能省掉逻辑面的三天。
- **别为看不见的东西写复杂修复。** 复杂修复留给有证据的缺陷；没有证据时该做的是加日志、加量测，让下一次能看见。DPI 那次的钳制代码就是反面教材——它正确、有测试、且在用户机器上空转。
- **指示器要能证伪自己。** 「链路正常」如果只要成功过一次就永远亮着，它就是在帮故障撒谎。
- **一个概念只允许一个函数。** 门控与护栏各算一套「重复」，用户就会拿到一个解释不通的死循环。
- **准确的错误信息不是修复。** 它只是让用户能看清自己还被困着。修到那儿之前，别把它当成交付。
- **静默吞错要当成 bug 排期**，不是「以后再说」。它的真实成本是下一个人在错误方向上耗掉的半天——比如我。
- **改代码的那个人负责同步文档与常量。** 文档里的数字和路径不是装饰，它们是最容易腐烂、也最容易误导人的部分。README 里那句「点击穿透」误导过我整整一轮。
- **断言要能证伪。** 你说「根因是 X」，就得说清「如果 X 不成立会看到什么」。我那条链就是被 `dockX=2251` 一个数字掀翻的。
- **「另一条路径看起来正常」不是排除证据，除非那个「正常」本身可证伪。** 第四轮我把「卡片用 800 且成功」当作排除传输问题的依据，而卡片的成功是静默模板兜底造出来的——一个假绿灯替另一个故障做了背书。
- **相关性不是因果，改常量前要先证明它是因。** 400→800 那次改动一行都没修好问题，却被我写成了「实测确认的根因」交付并推上 GitHub。**「实测」两个字只能用在被测量本身证实的事上。**
- **先只加诊断，跑一轮，让证据选假设，再动手。** 第四轮我把「猜的修复」和「诊断」塞进同一次改动，靠诊断自己推翻猜想去掉了错误成本——这是运气，不是方法。
- **「够不够大」问不出来就别问了，把那个数字删掉。** 第五轮用户一句「max_output_tokens 也不够大吧」点醒我：只要手写上限还在，这个悬案就永远悬着；而调大它会撞 provider 硬上限换 400，是换个死法。**好的收敛方向是让问题消失，不是让答案变大。**
- **规格里的数字先问它约束什么。** 「单次 ≤5k token」约束的是实际消耗（输入侧决定），不是输出上限。把它当上限去遵守，就会为一个不存在的约束保留一个制造悬案的数字。
- **改了代码要回扫所有陈述因果的文案。** 注释、断言消息、日志文案、错误提示里的"因为 X"，一旦 X 不再成立，那句话就从线索变成陷阱。
- **「我没搜到」不等于「它不存在」。** 第二轮写下这条，第三轮犯在「没查依赖默认值就断言没有文件日志」（第五节错 C），第五轮又犯在「逐端口扫没命中就断言代理没监听」（第五节错 D）。**同一条规矩我破过三次，而且每次的"搜法"都只有一种。** 复验要用**不同的查法**，否则只是把同一个盲区再看一遍。
- **允许推翻自己，但要留痕。** 被否证的假设连同证据一起写下来，比删掉更值钱。
- **动手前先读这份文档，尤其是第七、八节。** 第三轮我复犯了第七节明令禁止的事（从沙箱里起 KVBA），而禁令就写在 200 行外的文件里。规则存在不等于规则被加载——**读它**才是它起作用的前提。
- **有热重载的宿主上改代码 = 每次保存都是一次部署。** 一个编译错误就会带走用户正在跑的进程。落盘前先 `cargo check`。
- **铁律不是教条，是已经付过学费的地方。** 「绝不阻塞 Agent」这条，每加一个适配器都会被人试着绕过一次；绕之前请先读第六节。
- 这个项目只有你一个人长期在写。**注释要写给三周后完全忘了上下文的你。**
